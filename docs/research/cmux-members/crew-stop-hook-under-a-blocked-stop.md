# When forge's Stop hook blocks a crew member's stop, does the crew hook still mark it done and wake the lead?

## Answer
Yes, most likely. The two hooks are separate handlers on the same Stop event, and the engine runs all matching hooks in parallel, so a block from `verified-before-stop` does not stop `claude-crew.sh stop`. Each blocked stop therefore marks the member `done`, saves the last message as `report.md` and messages the lead, while the member goes on working. `crew.sh await` trusts the status field alone, so it would return on the first blocked stop. `bin/crew.mjs await` must not trust `done` by itself. For a slice member it must also check that `.forge/verify/<slice>.json` is green at the worktree's current HEAD, or that the slice is marked `red` in state (the third-block pass). No hook change is strictly needed; one optional change is listed at the end.

## Findings
- All matching hooks run in parallel, and hook entries merge across settings levels. forge's hook (plugin) and the crew hook (user settings) are different handlers, so neither is deduplicated away. ([hooks reference](https://code.claude.com/docs/en/hooks))
- A Stop block (`decision: "block"` or exit 2) "prevents Claude from stopping" and the reason goes back to Claude. The docs state no rule that a block cancels or skips the other Stop hooks. ([hooks reference](https://code.claude.com/docs/en/hooks))
- `stop_hook_active` is true when Claude Code is already continuing because of a stop hook. After 8 consecutive stop-hook continuations the engine overrides the block and ends the turn, so forge's 3-block cap sits under that limit. ([hooks reference](https://code.claude.com/docs/en/hooks))
- `last_assistant_message` is on the Stop payload, and it is what the crew hook saves as the report. ([hooks reference](https://code.claude.com/docs/en/hooks))
- `claude-crew.sh stop` is unconditional. It never reads `decision` or `stop_hook_active` and never talks to Claude. It runs `crew.sh sync <rec> done <report>` on every Stop. ([claude-crew.sh](/Users/mosica.bogdan/Desktop/personal/cmux-config/hooks/claude-crew.sh))
- `sync ... done` sets `status=done`, `done_at` and `summary`, and copies the message to `report.md`. It then sends `cmux agent message` to the orchestrator saying "finished: <summary>. Report: <path>". There is no dedup, so every Stop sends one message. ([crew.sh lines 123-181](/Users/mosica.bogdan/.config/cmux/scripts/crew.sh))
- `crew.sh await` counts only `status == running` as pending. A `done` record settles it and it prints `REPORT=<path>`. It reads no verify record. ([crew.sh lines 419-481](/Users/mosica.bogdan/.config/cmux/scripts/crew.sh))
- The only thing that flips a member back to `running` is the UserPromptSubmit hook (`prompt`) or `crew.sh send`. The SKILL says `done` means "its turn ends (Stop hook)". ([claude-crew.sh](/Users/mosica.bogdan/Desktop/personal/cmux-config/hooks/claude-crew.sh), [SKILL.md lines 75-83](/Users/mosica.bogdan/Desktop/personal/cmux-config/skills/cmux-crew/SKILL.md))
- forge's hook blocks while `.forge/verify/<slice>.json` is not green at HEAD. It counts denials in `.forge/verify/<slice>.denials`, ignores `stop_hook_active`, and blocks up to 3 times. The next stop passes with a `systemMessage`, marks the slice `red` in state and deletes the count. A fresh green record also deletes it. The hook is registered for both Stop and SubagentStop. ([verified-before-stop.mjs](/Users/mosica.bogdan/Desktop/personal/forge-sdlc/plugins/forge-sdlc/hooks/scripts/verified-before-stop.mjs), [hooks.json](/Users/mosica.bogdan/Desktop/personal/forge-sdlc/plugins/forge-sdlc/hooks/hooks.json), [ADR 0014](/Users/mosica.bogdan/Desktop/personal/forge-sdlc/docs/adr/0014-stop-gate-counts-instead-of-stop-hook-active.md))
- Together: stop 1 blocked gives done, a message and a premature report while the member keeps working, then stops 2 and 3 do the same, and the final stop (green, or the red pass) gives the last done and message. Up to four "finished" messages can reach the lead for one slice. The final `report.md` overwrites the earlier ones.
- Signals `bin/crew.mjs await` can read after a `done`:
  - Green and finished: the `<slice>.json` record has `green: true` and `head` equal to the worktree's `git rev-parse HEAD`, and `<slice>.denials` is absent.
  - Blocked and still working: no record, a stale record, or a red record, and `<slice>.denials` is present.
  - Red pass: state.json has the slice as `red` and `<slice>.denials` is gone.
  - These come from the code in `verified-before-stop.mjs` (`staleness`, `markRed` and the denials file), which is the same check the gate uses.

## Hypotheses
- Parallel execution means a blocking hook does not suppress the crew hook (hypothesis): the docs say hooks run in parallel but state nothing explicit about peers of a blocking Stop hook. A fixture run (a crew member with a forced red slice, watching `status` and the messages) would confirm it.
- A hook-forced continuation after a block does not fire UserPromptSubmit, so the record stays `done` while the member works (hypothesis): the same fixture run would show whether the `prompt` hook flips it to `running`. If it does fire, the status flickers but `await` could still return in the gap, so the verify check is needed either way.
- Optional hook change (hypothesis): make `claude-crew.sh stop` skip when the stop was blocked, for example by checking that `<slice>.denials` exists for the member's branch. That would couple the generic cmux-config hook to forge internals, so the await-side check is the better home.
