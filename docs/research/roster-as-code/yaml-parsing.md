# How do `lib.mjs` and the run pane mod both read `docs/agents/forge.yaml` with zero npm dependencies?

## Answer
Write a strict-subset YAML parser as ONE pure file with no imports, `plugins/forge-sdlc/hooks/yaml-subset.mjs` (or `.ts`), and import it from both sides: `lib.mjs` and the mod's `run-pane/*.ts`. Neither Node 22 nor the plugin engine offers a YAML parser, and a vendored full parser (`yaml` ISC, `js-yaml` MIT) is far more than the roster needs and makes the zero-dependency rule a vendoring exception. One file removes the mirror, so `tests/run-pane-config.test.mjs` needs no counterpart for YAML; keep only a fixture test of the parser itself.

Recommended grammar (a roster is only maps, string lists, scalars; reject everything else with a located error so a bad entry can be reported and skipped):
- Lines of 2-space indentation (tabs are an error). Blank lines and `# comment` lines are ignored; a trailing ` # comment` is stripped outside quotes.
- Map entry `key: value` or `key:` followed by a deeper-indented block. Keys: `[A-Za-z0-9_.-]+` or quoted.
- List: `- value` items at one indent (items are scalars; optionally `- key: value` flat maps if the schema ticket needs them).
- Scalars: plain (no `: ` or ` #` inside), `'single'` and `"double"` quoted (only `\"` and `\\` escapes), plus `true`/`false` as booleans, integers; `null`, `~` and empty as null. All else stays a string (so `disabled`, `claude-sonnet-5-5`, `plugin:agent` are strings; a colon not followed by a space is part of a plain scalar).
- Rejected with an error naming the line: anchors `&`, aliases `*`, tags `!`, merge `<<`, `|` and `>` block scalars, multi-line flow `[` `{` (a one-line `[a, b]` flow list of scalars may be allowed), multiple documents `---`, duplicate keys.
- API: `parseYamlSubset(text) -> { value, errors }` returning a plain object and located errors, never throwing, so the caller can ignore bad entries one by one as the map's constraint requires.

## Findings
- The repo has zero npm dependencies and requires Node >= 22 ([package.json](../../../package.json)); the map keeps that unless a ticket decides otherwise ([map.md](../../../docs/efforts/roster-as-code/map.md)).
- Node's own documentation (v22 `all.html`, first 100000 characters read) shows no YAML module or API ([Node 22 API docs](https://nodejs.org/docs/latest-v22.x/api/all.html)); a web search found no `node:yaml` core module either. The rest of the page was not read, see Hypotheses.
- The plugin engine's mod environment has "no DOM, no Node", no fs, and exposes no YAML parser in its declarations; its only YAML mentions are about how the engine reads skill frontmatter and hands it over as JSON ([claude-code.d.ts](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), header lines 14-27; `as YAML reads it` at line 13094).
- A mod and every file it imports from the plugin must be `.ts/.tsx/.jsx/.js/.mjs/.cjs/.mts/.cts`, an ES module with no `require`, loaded by `import` declaration; a module holding `import()` does not load ([claude-code.d.ts](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 19-25). So a single pure `.mjs`/`.ts` file with no imports and no Node APIs is loadable in the mod, and the mod already imports sibling `.ts` files (`./run-pane/config`, etc., [run-pane.tsx](../../../plugins/forge-sdlc/hooks/run-pane.tsx) lines 62-75).
- The mod cannot import `lib.mjs` because it pulls in `node:child_process`, `node:fs`, `node:path` ([lib.mjs](../../../plugins/forge-sdlc/hooks/scripts/lib.mjs) lines 5-7). `config.ts` is the mirror written for that reason and carries "No imports, so node tests load it as it is" ([config.ts](../../../plugins/forge-sdlc/hooks/run-pane/config.ts) lines 1-6); the mirror is held by [tests/run-pane-config.test.mjs](../../../tests/run-pane-config.test.mjs). A pure shared file avoids the mirror because the node-only part is not in it.
- The mod already hand-reads agent frontmatter with a regex rather than a parser ([routing.ts](../../../plugins/forge-sdlc/hooks/run-pane/routing.ts) lines 65-73), so a hand-written subset matches existing practice.
- Vendoring options: `yaml` (eemeli) is ISC licensed, dependency-free ([LICENSE](https://raw.githubusercontent.com/eemeli/yaml/main/LICENSE), [repo](https://github.com/eemeli/yaml)); `js-yaml` 5.5.0 is MIT with one runtime dependency, `argparse` (dist `js-yaml.mjs` ESM entry exists) ([package.json](https://raw.githubusercontent.com/nodeca/js-yaml/master/package.json)). Both are full YAML 1.2 parsers: far above the need, and a vendored bundle must be re-synced and audited for upstream CVEs.
- Existing YAML in this repo is frontmatter and eval `case.yaml`, none read at run time by the hooks ([contracts.md](../../../docs/contracts.md) line 90; [ADR 0013](../../../docs/adr/0013-evals-under-the-plugin.md) line 11); so no parser exists to reuse.

## Hypotheses
- Node 22 ships no YAML parser beyond what the first 100000 characters of its API docs showed (hypothesis): confirm by searching the full `all.html` or `node -e "require('node:yaml')"` under Node 22.
- The mod bundler resolves an explicit-extension relative import (`./yaml-subset.mjs`) from a `.ts` file, and `lib.mjs` can import a file under `hooks/` outside `hooks/scripts/` (hypothesis): confirm with a one-file spike and `claude plugin validate` plus `claude plugin test`.
- Node's type stripping loads a shared `.ts` file if `lib.mjs` imports it by explicit `.ts` extension (hypothesis, the existing test does import `config.ts` this way, but a `.mjs` runtime import of `.ts` is untested): prefer `.mjs` with JSDoc types to sidestep it.
- The roster needs only flat lists of scalars and maps up to three levels deep (hypothesis): confirm when the schema ticket (The forge.yaml schema) lands; add `- key: value` list-of-maps to the grammar only if it does.
