# Can a hook or the mod rewrite an Agent or Skill call's target, and can a hook deny one?

## Answer
Agent: yes, transparently, in the mod. `agent.spawn` lets a hook rewrite `subagentType` (to another agent the call can dispatch, exactly), `model`, `prompt`, `description`, `background` and `cwd`, so the same hook that applies routing today can swap the agent for a role and the lead's call sites need no resolver. Do it at `agent.spawn`, not at a PreToolUse `updatedInput` or `tool.call`: a changed input there lands after auto mode reviewed it and can be denied. A swapped agent runs its own definition (system prompt, tools) with the call's `prompt` unchanged, so the brief written for `forge-sdlc:implementer` reaches it as is.
Skill: no documented transparent path to swap the skill. PreToolUse `updatedInput` replaces a tool's whole input generically, and the engine types Skill as `{ skill, args? }`, but nothing in the docs or declarations says a rewritten `skill` is honoured, and it carries the auto-mode problem; `skill.prompt` can only replace the text the model reads (it can implement "disabled" or a swap by returning other text, but the Skill call, its grants and its name stay the original). The Skill swap should stay with the resolver unless a live test (hypothesis below) passes.
Enforcement: a PreToolUse command hook can deny an Agent or Skill call with a reason in every mode, and the payload says whether the caller is the lead or a member (`agent_id` present only inside a subagent or teammate), so enforcement is feasible as designed.

## Findings
- A PreToolUse `updatedInput` "replaces the entire input object", needs no `permissionDecision`, and permission rules are evaluated against the returned input ([hooks reference](https://code.claude.com/docs/en/hooks), PreToolUse decision control).
- With `updatedInput` and no `permissionDecision` in auto mode, the changed call can be denied with "a hook changed this call's input after auto mode reviewed it"; pairing `allow` skips that but `allow` also skips the prompt ([hooks reference](https://code.claude.com/docs/en/hooks), auto mode interaction).
- This repo already hit that: the mod's crew naming runs on `agent.spawn`, "never `tool.call`: a rewritten call lands after auto mode reviewed it, so every dispatch was refused once" ([run-pane.tsx header](../../../plugins/forge-sdlc/hooks/run-pane.tsx), lines 33-41, and comment at 211-218).
- `agent.spawn`'s `subagentType` is rewritable: "A rewrite names another agent this call can dispatch, exactly. That definition is the one spawned; a name matching none refuses the spawn, and a fork dispatches no other." A teammate's type may be a role no definition has. Rewritable keys: prompt, description, subagentType, model, background, cwd; `provider`, `name`, `fork`, `isTeammate`, `parentAgentId`, `tool_use_id` are pinned; a `resume` spawn can only be refused; a workflow agent honours only `prompt` and `model` ([AgentSpawnInput](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 254-410).
- The mod's `routedSpawn` already rewrites `model` through `next({ ...e, model })` at `agent.spawn`, keyed on `e.subagentType` ([run-pane.tsx](../../../plugins/forge-sdlc/hooks/run-pane.tsx), lines 276-294 and 438-447). Changing `subagentType` in the same object is the same mechanism. Caveats: the effort and routing record are keyed by `e.subagentType`, so after a swap the entry must be looked up by the role (the original type), and `readFrontmatter` reads `agents/<role>.md` of this plugin, which a swapped-in agent does not have (its frontmatter defaults are unknown, so the "overridden" mark must be computed against the definition that will run).
- What the swapped agent sees: the spawn's `prompt` is "the task the subagent is given", and a rewrite of `prompt` is "the prompt the subagent runs with"; `subagentType` selects "the definition ... spawned", so the system prompt is the new agent's own and the call's `prompt` (the brief) is untouched unless the hook rewrites it ([AgentSpawnInput](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 272-294). The Agent tool's own parameters are `description`, `prompt`, `subagent_type`, `model`, `effort`, `name`, `isolation` ([tool schema](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 17611-17630). Gap: nothing says what happens to a call's `isolation` or to tool grants the original agent had; the brief's conventions (worktree, proof, `bin/` commands) are the replacement agent's to follow, since its prompt does not know them (hypothesis on how well it does).
- A model-facing alternative for hiding types: `agent.offer` returns `{ isOffered: false }` for a type, in the listing and at dispatch, but it is model-facing only and "a plugin's own `$.agent.spawn` of a type is no offer" ([AgentOfferInput](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 206-242). Useful for enforcement alongside the deny hook.
- The mod can also refuse a spawn: `agent.spawn` may return `{ deny: reason }`, "the Agent tool's error" ([AgentSpawnResult](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 423-461). A guard that throws is skipped and the call proceeds unless it has `.catch` ([EngineEventOf](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 4119-4137), so the mod fails open by default; a command hook failing is also exit 1 with no decision ([lib.mjs `run`](../../../plugins/forge-sdlc/hooks/scripts/lib.mjs), lines 474-490).
- The Skill tool's input is `{ skill: string, args?: string }` ([tool schema](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 18334-18339). `tool.call` is a union discriminated by `tool` where "a rewrite is checked against [the tool's] schema" and only `tool`, `tool_use_id`, `agentId` are reserved ([ToolCallInput](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 14085-14096), so a Skill `skill` rewrite at `tool.call` is type-legal, but it is raised before the mode's check and carries the auto-mode review gap above.
- There is no `skill.spawn` equivalent. `skill.prompt` fires when the engine expands a skill's prompt (`/name`, the Skill tool, a preload); a hook returns `{ text }` "instead", and receives `skill`, `text`, `frontmatter`, `source`, `pluginName` ([SkillPromptInput](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 4496-4506 and 13136-13180). It changes what the model reads, not which skill ran; typed `/skillname` bypasses PreToolUse ([hooks reference](https://code.claude.com/docs/en/hooks)).
- A PreToolUse command hook can deny: `hookSpecificOutput.permissionDecision: "deny"` with `permissionDecisionReason`; exit 2 also blocks with stderr as the reason; deny wins over allow, ask and defer when hooks disagree; deny and ask rules are still evaluated regardless ([hooks reference](https://code.claude.com/docs/en/hooks)). The plugin's helper is `deny(reason)`, documented "Holds in every permission mode" ([lib.mjs](../../../plugins/forge-sdlc/hooks/scripts/lib.mjs), lines 463-466). Matchers on tool name accept exact names and `|` lists, so `Agent|Skill` is a valid matcher ([hooks reference](https://code.claude.com/docs/en/hooks)); today's `hooks.json` registers `*` for `context-budget.mjs` and no `Agent` or `Skill` matcher ([hooks.json](../../../plugins/forge-sdlc/hooks/hooks.json)).
- Caller identity: common hook input has `agent_id` ("the subagent or in-process teammate the hook fires in") and `agent_type` ("present when the session uses `--agent` or the hook fires inside a subagent") ([hooks reference](https://code.claude.com/docs/en/hooks), common input fields). `context-budget.mjs` already relies on it: "the main session is never blocked" because only a subagent's payload carries `agent_id` ([context-budget.mjs](../../../plugins/forge-sdlc/hooks/scripts/context-budget.mjs), lines 5, 80, 93). In the mod the same fact is `parentAgentId` (absent from main) on `agent.spawn` and `agentId` on `tool.call` ([AgentSpawnInput](../../../plugins/forge-sdlc/hooks/types/claude-code.d.ts), lines 314-322).
- The multi-hook merge of several PreToolUse `updatedInput`s is not stated in the excerpt read; the first 200,000 of 294,000 characters of the reference were read, and the Skill tool had no `tool_input` page there ([hooks reference](https://code.claude.com/docs/en/hooks)).

## Hypotheses
- A PreToolUse or `tool.call` rewrite of the Skill tool's `skill` is honoured by the engine and the new skill's text is what the model reads (hypothesis): a throwaway session with a `PreToolUse` `Skill` hook returning `updatedInput: { skill: "<other>" }` with `allow`, then reading the transcript for which SKILL.md loaded.
- A PreToolUse `updatedInput` of `subagent_type` is honoured by the Agent tool (hypothesis): same test; moot if the mod's `agent.spawn` rewrite is the chosen path, but it would be the only path for the prior-sdlc plugin's command hooks if its mod is absent.
- A rewritten `subagentType` at `agent.spawn` is not subject to the auto-mode review that refused call rewrites (hypothesis): the repo's crew code relies on this for `description` and `name`, but not for `subagentType`; a live spawn in auto mode with a swapped type confirms it, and a test in `run-pane.routing.test.tsx` style covers the type's mapping only against the stand-in host.
- A swapped-in agent that lacks this plugin's `bin/` conventions (worktree, proof, `crew-name`) still completes a slice from the brief (hypothesis): run one build slice with a swapped implementer; depends on the brief's text and the replacement's definition.
- Two PreToolUse hooks that both return `updatedInput` apply last-wins or error (hypothesis): read the remaining part of the hooks reference (offset 200000) or test.
